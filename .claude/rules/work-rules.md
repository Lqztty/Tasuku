# 作業ルール

## 必須ルール

1. **言語**: 素の日本語で簡潔に書く
2. **Docker**: npm→`docker compose exec node` / php→`docker compose exec app`
3. **学習メモリ**: セッション開始時 `memories/learnings.md` 読込
4. **承認フロー**: 小規模は即実装可。中規模以上は計画→承認→実装
5. **レビュー**: ユーザー動作確認後に開始
6. **ビルド**: ブラウザ確認後に実行。実装直後禁止
7. **完了後**: 追加要望あれば新ブランチ提案
8. **仮説柔軟性**: 2回失敗→視点転換、3回→ユーザー報告

## 誰が作業するか

**基本はメインが自分で調べ、自分で書く。**
係 (サブエージェント) に渡すと、係は同じファイルを最初から読み直し、
メインが把握していた前提は依頼文に書いた分しか伝わらない。
小〜中規模の作業はメインが通しでやる方が速く、食い違いも起きにくい。

係に渡すのは次の3つの場面だけ:

| 場面 | 使うもの |
|------|---------|
| どこにあるか見当がつかない広い検索で、結論だけ欲しいとき | 組み込みの `Explore` |
| 互いに依存しない作業を並行で進めたいとき | 組み込みの `general-purpose` (worktree で分離) |
| 書いた本人とは別の目で差分を見たいとき | `/code-review` |

- 係には**結論と該当箇所 (ファイル名:行番号) だけ返させる**。ファイルの中身を持ち帰らせない
- 係の結論はメインが確かめてから使う。修正の根拠になる箇所はメインが自分で読む
- 複数の係を起動したときは、誰に何を投げたかを1行ずつ書く
- 作業ごとの担当表や「Nファイル以上の調査は必ず委任」のような機械的な委任ルールは置かない
  (小さいモデルの調査結論を前提に進めて外れ、メインが読み直す二度手間が出たため)

## 実行コストの規律

会話が長くなるほど1回の応答が高くなる (毎回それまでの全履歴を読み直すため)。
実測では長時間セッション上位26本が全体の86%を占めていた。

- **1つの作業 (PR単位) が終わったら `/clear` する。** 次の作業を同じ会話で続けない
- 会話が長引いてきたら `/session-carryover` で「続ける/compact する/切る」を判定させる
- ファイル全体の読み込みを避ける。`sed -n '120,180p'` や grep で必要な範囲だけ見る
- 同じファイルを確認のために読み直さない (編集が失敗すればエラーが返る)
- ビルド・テストの長い出力はそのまま貼らない。件数と失敗行だけ残す

## スキル自動起動

- ユーザーがスキル名を言わなくても、依頼内容が一致したら最初にスキルを起動
- 「明示されていないので使わない」は禁止
- 複数候補がある時は、最も効果の高い最小セットだけ起動

## 小規模変更の定義

- 変更ファイル 1〜2
- 1レイヤまたは1機能で完結
- migration / schema / seed 変更なし
- API / route / request / validation / store contract変更なし
- auth / permission / security / data integrity影響なし
- shared component新設なし（既存の共通部品をpropsで拡張するのは可）
- 影響範囲が局所的で、最小テストまたは局所確認ができる

上記をすべて満たす場合は承認待ちせず着手してよい。
1つでも外れる場合は計画と承認を取る。
